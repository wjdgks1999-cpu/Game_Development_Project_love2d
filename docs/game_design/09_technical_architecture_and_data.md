# 기술 구조와 데이터

## 1. 목적과 조건

LÖVE·Lua 기반 Android 버티컬 슬라이스의 런타임, 데이터, 저장, 난수, 로그와 테스트 구조를 정의한다.

- [확정] Android 가로 화면, 1280×720 논리 해상도, 안정적인 30FPS를 목표로 한다.
- [확정] 오프라인 단일 플레이이며 서버·계정·생성형 AI·외부 AI API를 사용하지 않는다.
- [확정] 범용 ECS 대신 장면 스택과 독립 시스템을 사용한다.
- [확정] 경기 규칙은 렌더링·사운드와 분리하고 상태 변화는 명시적인 사건으로 처리한다.

## 2. 모듈 구조

### 최상위

- `App`: 초기화, 데이터 검증, 저장, Android 중단·복귀와 오류 처리
- `SceneStack`: 타이틀, 대화, 경기, 결과, 프로그램, 일정, 훈련, 휴대폰과 엔딩
- `OverlayStack`: 일시정지, 튜토리얼, 프로그램 패널과 알림
- `GameSession`: 선수·퀘스트·커리어·여론·체크포인트의 단일 진실 원본

### 시스템

- `MatchSimulation`: 투구부터 등판 종료까지의 순수 경기 판정
- `PitchResolver`, `BatterAI`, `ContactResolver`, `BattedBallResolver`, `DefenseResolver`, `ResponsibilityResolver`
- `TrainingSystem`, `ProgressionSystem`, `QuestSystem`, `PassiveSystem`, `CareerSystem`
- `NarrativeSystem`, `CommunitySelector`, `PublicFactBuilder`, `TemplateValidator`
- `InputService`, `ResolutionService`, `RngService`, `SaveService`, `AudioService`, `HapticService`, `LogService`

장면은 `GameSession`을 직접 임의 수정하지 않고 시스템 명령과 사건을 사용한다. 애니메이션, UI, 사운드와 파티클은 경기 난수나 결과를 변경하지 않는다.

## 3. 시간·입력·해상도

- 목표 프레임 시간은 약 33.3ms다.
- 렌더링은 30FPS를 기준으로 하지만 릴리스는 프레임 번호가 아닌 실제 터치 시각으로 판정한다.
- 공, 링과 애니메이션은 경과 시간으로 보간한다.
- 큰 델타타임이 발생하면 시간을 진행하지 않고 일시정지·복구한다.

터치에는 실제 시각, 물리·논리 좌표, 포인터 ID, 활성 장면과 입력 대상을 기록한다. 실제 화면에서 안전 여백과 균등 배율을 계산한 뒤 1280×720 좌표로 역변환한다. 포커스를 잃으면 활성 터치를 모두 취소한다.

## 4. 경기 처리 순서

실제 구현의 세부 계산 순서와 단계별 입력·출력은 `contracts/01_match_resolution_contract.md`를 따른다.

1. 상황 스냅샷
2. 구종·목표·사인 기록
3. 투구·릴리스 시각
4. 실제 위치·구속·움직임
5. 타자 예상과 접근
6. 지켜보기·스윙
7. 헛스윙·파울·인플레이
8. 타구 질과 궤적
9. 자동 수비·주루
10. 투수 책임
11. 카운트·주자·점수
12. 멘탈·피로
13. 퀘스트 사건과 로그
14. 다음 투구·타자·종료

각 단계는 명시적인 입력·출력 데이터만 사용한다.

## 5. 첫 프롤로그 예외

`PrologueConstraint`는 별도 모듈로 격리한다.

- 첫 1군 프롤로그에서만 활성화한다.
- 세 번째 아웃 전에 최소 한 점의 투수 책임 실점을 보장한다.
- 좋은 입력을 실투로 바꾸지 않고 모순되지 않는 사건을 선택한다.
- 작동 여부와 사건을 개발 로그에 기록한다.
- 2군 평가와 최종 1군 등판에서는 생성·호출하지 않는다.

## 6. 난수

- 전역 `math.random`을 직접 사용하지 않는다.
- 마스터 시드에서 `pitch_spread`, `batter_decision`, `contact`, `batted_ball`, `defense`, `training`, `community` 스트림을 분리한다.
- UI·사운드·파티클은 경기 난수를 사용하지 않는다.
- 스트림 상태와 호출 횟수를 기록·직렬화한다.
- 같은 빌드·데이터·상태·시드·입력·호출 순서에서 같은 결과를 재현한다.
- 다른 버전 사이의 완전한 난수 호환은 보장하지 않는다.

## 7. 데이터 형식

- 선수·구종·타자·경기·훈련·퀘스트·패시브·대사·템플릿·밸런스: 읽기 전용 Lua 테이블
- 체크포인트·설정·저장: JSON
- 개발 사건 로그: JSON Lines
- JSON은 단일 래퍼 모듈을 통해 처리한다.
- 저장에는 스키마·빌드·데이터 버전을 기록한다.

## 8. 핵심 스키마

### 선수

| 필드 | 타입·범위 | 관계·예시 |
| --- | --- | --- |
| `id`, `display_name` | string, 필수 | 모든 참조 키 |
| `age`, `throws` | integer, enum | 26, `R` |
| `control`, `stuff`, `velocity`, `stamina`, `mental` | integer 0~100 | 투구·상태 판정 |
| `pitch_mastery` | table 0~100 | 구종 ID별 숙련도 |
| `condition`, `fatigue` | integer 0~100 | 세션 상태 |
| `roster_level`, `passives` | enum, array | 커리어·패시브 |

### 구종

`id`, `display_name`, `velocity_min/max`, `base_spread`, `timing_window`, `ring_speed`, `break_x/y`, `fatigue_cost`, `stuff_factor`, `tunnel_group`을 가진다.

### 타자

`id`, `bats`, `contact`, `power`, `discipline`, `adaptation`, 공개 성향 최대 2개, 구종·코스 선호도와 리그 수준을 가진다.

### 경기

`id`, `scene_role`, 이닝·초말·점수·아웃·주자, 타순, 팀 수비력, 퀘스트 ID와 `prologue_constraint`를 가진다.

### 훈련

`id`, 12구 구성, 점수 비중, 등급 경계, 등급별 성장, 컨디션·피로 변화와 퀘스트 태그를 가진다.

### 퀘스트·패시브

퀘스트는 ID, 표시 문구, 발생·기한·성공·실패·예외·보상·실패 전환과 공개 진행도를 가진다. 패시브는 발동 사건, 범위, 최대 횟수, 지속 투구, 효과 종류·값, 만료 조건과 공개 여부를 가진다.

### 사건·템플릿

사건 코드와 공통 필드는 `contracts/02_game_event_contract.md`, 채널별 콘텐츠 필드와 출력 관계는 `contracts/03_community_content_schema.md`를 따른다. 실제 데이터 준비 상태는 `content/CONTENT_REQUIREMENTS.md`를 확인한다.

사건은 ID, 유형, 출처, 시각, 중요도 0~3, 태그, 책임, 공개 수준과 payload를 가진다. 템플릿은 채널, 페르소나, 어조, 필수·금지 태그, 여론 단계, 중요도, 슬롯, 가중치, cooldown, 의미 그룹과 문장을 가진다.

모든 필드는 필수 여부, 타입, 범위, 기본값과 참조 관계를 데이터 검증기에 등록한다.

## 9. 데이터 검증

시작 시 ID 중복, 필수 필드, 숫자 범위, 참조 ID, 퀘스트 조건 충돌, 구속 범위, 템플릿 태그·슬롯, 장면 연결과 저장 버전을 검사한다. 개발 빌드는 상세 오류를, 테스트 빌드는 안전한 오류 화면과 로그를 제공한다.

## 10. 시스템 처리

- `ProgressionSystem`: 일반 성장, 프로그램 보상, 0~100 제한과 상태 변화
- `QuestSystem`: 사건을 구독해 제시·진행·성공 예정·성공·실패·만료 관리
- `PassiveSystem`: 발동, 타석별 횟수, 다음 투구 적용과 만료
- `CareerSystem`: 강등, 2군 평가, 재콜업, 최종 판정과 엔딩
- `CommunitySelector`: 공개 사건 요약, 후보 필터, 가중치 선택, 슬롯·사실 검증과 폴백

감독 평가는 숨은 합격 조건으로 사용하지 않는다. 휴대폰 반응은 공개 사건 확정 시 생성하며 열람 시점에 다시 선택하지 않는다.

## 11. 저장·체크포인트

- 현재 자동 저장 1개와 이전 정상 저장 백업 1개를 둔다.
- 첫 강등, 프로그램 발현, 각 일정 행동 완료, 2군 평가 직전과 최종 등판 직전에 체크포인트를 만든다.
- 임시 파일 기록·검증 후 본 저장으로 교체하고 기존 정상 저장은 백업한다.
- 현재 저장 손상 시 백업을 자동 검증·복구한다.
- 원본 템플릿 문장 대신 ID와 슬롯, 읽음 상태를 저장한다.

저장에는 버전, 플레이 경로, 장면, 선수·퀘스트·패시브·커리어, 체크포인트, 시드·난수 상태, 커뮤니티 반응, 튜토리얼과 재시도 횟수를 포함한다.

경기 중에는 타자 시작 스냅샷, 훈련 중에는 12구 훈련 시작 스냅샷으로 복구한다. 같은 시드를 사용하며 완료된 이전 결과와 확정 보상은 유지한다.

## 12. 로그

투구 로그에는 경기·타자·투구 ID, 시드, 구종·사인·목표·실제 위치, 릴리스 시각, 능력치·상태 영향, 타자 판단, 타격·수비·책임, 멘탈·피로와 프롤로그 제약을 기록한다.

시스템 로그에는 훈련·성장, 퀘스트, 패시브, 커리어, 템플릿 선택·폴백, 저장·복구, 오류와 성능을 기록한다. 외부 서버로 전송하지 않는다.

## 13. 디버그 메뉴

개발 빌드에서 장면 이동, 선수·상태 설정, 훈련 등급과 퀘스트 강제, 시드 고정, 프롤로그 제약, 타자·카운트·주자, 타구·실책·불운, 여론·태그·템플릿, 엔딩, 저장 손상과 FPS를 직접 시험한다.

최종 비공개 테스트 빌드에서는 기본 비활성화하고 빌드 플래그나 숨겨진 개발 조작으로만 활성화한다.

## 14. 자동 테스트

통합 검증 목표의 상태, 통과 기준, 증거는 `VALIDATION_MATRIX.md`에서 관리한다.

- 릴리스 방향, 산포 한계, 상태 단계와 스트라이크 경계
- 훈련 점수·성장 상한과 `루틴 복구`
- 가상 아웃과 책임 판정
- 같은 시드·입력의 동일 결과와 UI 난수 분리
- 첫 프롤로그에서만 제약 작동
- 2군·최종 경기의 비고정 결과
- 실책·불운 예외와 퀘스트 성공·실패
- 데이터 참조·템플릿 슬롯·공개 정보
- 저장 동등성, 손상 복구, 마이그레이션과 중복 보상 방지

## 15. 성능·Android 빌드

- 사용자 보유 Android 기기에서 안정적인 30FPS, 약 33.3ms 프레임을 목표로 한다.
- 우선순위는 입력, 링·공, 판정, 캐릭터, HUD, 핵심 사운드, 배경 효과 순이다.
- 부족하면 관중, 배경 파티클, 잔상과 비핵심 UI 효과부터 줄인다.
- 가로 고정, 내부 저장, 오프라인 실행, 불필요한 네트워크 권한 제외와 빌드별 로그·개발 메뉴 설정을 확인한다.

## 16. 오류·버전

- 경기 판정 오류는 불완전한 결과를 확정하지 않고 타자 시작으로 복구한다.
- 템플릿 오류는 안전한 폴백으로 대체해 경기 진행을 막지 않는다.
- 저장에는 `save_schema_version`, `game_build_version`, `data_version`을 기록한다.
- 마이그레이션 전 백업하고 변환 불가능하면 안전한 체크포인트나 새 게임을 안내한다.

## 17. 제외 범위

범용 ECS, 온라인 서버·계정·클라우드, 멀티플레이, 원격 설정, 외부 분석·광고·결제 SDK, 생성형 AI·외부 AI API, 범용 스크립트·플러그인 시스템과 모든 버전 간 난수 호환을 제외한다.

## 18. 구현 우선순위

1. App·장면·오버레이·GameSession
2. 해상도·멀티터치·입력 시각
3. 데이터 로더·검증과 난수·로그
4. 투구·타자·타격·수비·책임
5. 경기 장면과 30FPS 검증
6. 훈련·성장·퀘스트·패시브
7. 저장·백업·복구
8. 커리어·엔딩과 커뮤니티

## 19. 완료 기준

- [확정] 장면·오버레이와 게임 상태가 분리된다.
- [확정] 경기 로직과 표현이 분리되고 정적 데이터가 코드 밖에 있다.
- [확정] 데이터 필드·범위·참조를 검증한다.
- [확정] 독립 난수 스트림으로 결과를 재현한다.
- [확정] 프롤로그 제약이 다른 경기와 격리된다.
- [확정] 퀘스트·책임·커뮤니티가 같은 사건 로그를 사용한다.
- [확정] 자동 저장·백업과 경기·훈련 복구가 동작한다.
- [확정] 주요 경로를 디버그 메뉴와 자동 테스트로 검증한다.
- [확정] 최종 빌드에서 개발 메뉴가 기본 비활성화된다.
- [검증 필요] 실제 Android 기기에서 안정적인 30FPS, 입력 지연, 메모리, 저장과 복귀를 확인한다.
